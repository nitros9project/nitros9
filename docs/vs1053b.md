# The VS1053b real-time MIDI strap and the switcher (vs edition 10)

Foenix F256 K2 and Jr2, NitrOS-9 WildBits port, branch `wb/vs1053`. Written 2026-09-07 from the bench work of
2026-09-06/07 and a dump of the chip's own ROM. The VS1053b is the MP3/OGG/WAV/AAC/WMA decoder and General MIDI
synthesizer behind the FPGA bridge at $FF50 (bridge registers: the kit's `wildbits-<machine>-rc12-vs1053-bridge.md`).

## 1. Who this is for

- **Owners of a Jr2 from the PCB run that ties the VS1053b's GPIO1 (LQFP-48 pin 34) to VCC.** That chip powers up as
  a real-time MIDI synthesizer: it answers SCI, plays MIDI events sent over SDI, but decodes no stream at all - no MP3,
  OGG, WAV, AAC, WMA and no MIDI files. The board's author cured her boards with a solder blob across pins 33 and 34
  (GPIO0 to GPIO1). The switcher is the software equivalent: with `vs` edition 10 on the disk, a strapped chip is moved
  to the stream decoder after every reset, and nothing on the board changes.
- **Anyone who wants to move the chip between its two personalities on purpose**, on either machine: `vs -n` makes it a
  synthesizer (MIDI events over SDI, General MIDI voices), `vs -o` makes it a stream decoder again. No reset either way.
- **Programmers.** The plug-in files in `SYS/VSPLUGINS` are plain word lists that any program can send over SCI; the
  record format and every address involved are in this document.

Symptoms of a strapped chip, from the Jr2 bench of 2026-09-06 (before the bridge): `vs -i` shows `GPIO IN ($C018) $0A02`
(bit 1 = GPIO1 high) and AUDATA $AC45; the SDI sine test is silent while the SCI sine and the RT-MIDI piano note are
audible; a file "plays" with HDAT1 stuck at $0000, SM_CANCEL never clears at the end, DECODE_TIME counts uptime
(283 s seen) instead of seconds decoded; a pop when the analog stage comes up.

## 2. Intent

1. A strapped Jr2 must play files with nothing but the disk. The switcher's bytes live inside `vs` (the `Switch`
   table), and `vs` sends them by itself whenever it has just reset the chip and the pins read as the strap.
2. The same bytes ship as a file, `SYS/VSPLUGINS/switcher.plg`, for other programs and for experiments with `vs -l`.
3. Manual control of the mode on any board (`-n`, `-o`), because the synthesizer is worth having on the K2 too.
4. Nothing in the cores changes. The K2 rc13 STRAP register experiment (a register bit on FPGA pin V1) was scrubbed
   once the bench showed V1 drives GPIO0, not GPIO1; neither machine has an FPGA pin that reaches GPIO1.

## 3. What the chip does at power-up

The VS1053b samples two GPIO pins while it comes out of reset (datasheet v1.13, the boot sections; copies in
`wildbits-buildkit\vs1053\`):

| GPIO0 (pin 33) | GPIO1 (pin 34) | boot |
|---|---|---|
| 0 | 0 | stream decoder (normal) |
| 0 | 1 | real-time MIDI synthesizer |
| 1 | any | SPI boot: looks for an EEPROM, finds none, runs the stream decoder |

- **K2:** FPGA pin V1 (XDC name `VS1053_MIDI_RT_o`, in truth the chip's GPIO0) is driven low by the core; GPIO1 has a
  board pull-down. `vs -i` reads GPIO IN $0A00: decoder.
- **Jr2, bad PCB run:** GPIO1 tied to VCC, no FPGA pin on either strap. GPIO IN $0A02: synthesizer.
- **Jr2 with the pin 33-34 bridge:** GPIO0 follows GPIO1 high and the SPI boot wins. GPIO IN $0A03: decoder (bench
  2026-09-06 22:1x: `vs -t` sine audible, `vs -c C0 -s some.mp3` plays).

Every reset re-samples the pins: the bridge's hardware reset (CTRL bit 3, the chip's XRESET), the board's cold reset,
and a software reset (MODE bit 2, SM_RESET). The chip clears its own GPIO direction register before it samples, so a
program cannot make the chip drive its straps low and re-boot - editions 1-3 of `vs` tried exactly that from inside the
chip, and the pins read the same afterwards.

### The mode flag inside the ROM

The firmware keeps the mode in one I/O location, X:$C04C. Two tiny ROM routines set and clear it:

```
2135  ldc 0xc04c,i7        RtMidiStart
2136  ldc 0x0001,i5
2137  stx i5,(i7)          X:$C04C := 1
213b  jr

213d  ldc 0xc04c,i7        the mirror
213e  ldc 0x0000,i5
213f  stx i5,(i7)          X:$C04C := 0
2141  jr
```

$2135 is what VLSI's real-time MIDI start plugin calls, and what the boot code calls when the strap says so. The
stream-signature dispatcher calls it too ($29A5, $29BE, after matching "MT" = MThd, a Standard MIDI File): the MIDI-file
player and the real-time mode are the same synthesizer engine, fed from a file or from live events.

## 4. Reading the ROM

Everything in this document that names a ROM address comes from a dump of the chip's ROM, read from the K2 on
2026-09-07 with `vs -u aaaa nnnn <file>`: WRAMADDR $8000+aaaa opens the instruction-memory window, two WRAM reads per
32-bit word, high half first. Visible: I:$0000-$3FFF (IRAM $0000-$0FFF, its mirror at $1000-$1FFF, ROM $2000-$3FFF).
The rest of the ROM - the visible code calls $47C5, $4E66, $5119, $8014 - cannot be read over SCI. The dump is
`wildbits-buildkit\vs1053\rom.bin` (65,535 words). It was taken with VLSI's patches package loaded, so IRAM $0050-$0FFF
holds the patches, which is how their restart code was read.

Tools, all in `wildbits-buildkit\tools\`:

- `plg2bin.py` converts VLSI's `.plg` / `.c` word arrays into the raw big-endian files `vs -l` sends, walking the
  record format to validate them.
- `vsdsp4dis.py` is a small VSDSP4 disassembler (VSDSP4 user manual chapter 7: LDC, the control opcodes, double moves,
  ALU operations with parallel moves). `vsdsp4dis.py rom.bin 3f84 90` lists a range; `find` lists GPIO reads and
  references to $2135.
- `mkswitcher.py` assembles the switcher and writes `media/vsplugins/switcher.plg` plus the `fdb` lines for `vs.asm`.

### The session routine at $3F84

The hidden main loop calls this routine for every stream - after a file ends, after SM_CANCEL, after any reset. It is
the reason no restart cures a strapped chip:

```
3f84  stx mr0,(i6)+1 ; sty i7,(i6)     save registers
...
3f8e  call 0x2190                       init subroutines $2190, $3879, $2712,
3f93  call 0x2712                       $3020 (i2 = MODE), $26A7
3f97  ldc 0x1f40,a0                     AUDATA := $1F40, the idle decoder's 8 kHz
3fa2  ldx a0,(i2) / and a0,a1,a0        MODE & $1000 (SM_ADPCM) -> call 0x5119, recording only
3fb0  call 0x31cc                       last init call
3fb2  ldx null,(i6)-1 ; ldy null,(i1)-2 i1 := $C018
3fb3  ldx a0,(i1)                       a0 := GPIO_IDATA             <- the strap read
3fb4  and a0,a1,a0                      a0 := GPIO & 3
3fb5  add a1,ones,a1                    a1 := 2
3fb6  sub a0,a1,a1                      a1 := (GPIO & 3) - 2
3fb7  ldc 0x0000,NOP                    nop                          <- the switcher hooks here
3fb8  jzc 0x3fd5                        not 2: continue at $3FD5
3fba-3fd2                               strapped: GPIO2/GPIO3 folded into MODE bits 4/7
                                        (EarSpeaker), Y:$1B19 := 8
3fd3  call 0x2135                       X:$C04C := 1 - the synthesizer
3fd5  call 0x27e1                       both paths: start the session
3fd7  call 0x2c6a                       the session loop: service the stream,
...   jzs 0x3fd7                        until d0 != 0 (end of stream / cancel)
3fe9-3ff1                               restore registers, jr
```

The strap is not a one-time boot decision: the ROM reads the pins again at the start of every session.

### How VLSI's patches package restarts the firmware

The patches package (`vs1053b_patches.plg`, 4667 words) ends with AIADDR := $50. IRAM $50 is `j $300`, and
$300-$32B is VLSI's restart:

```
0300-0305   X:$1E49 := 0; STATUS &= $7FFF (bit 15, SS_DO_NOT_JUMP, off)
0306-030a   X:$1802 := 0, X:$1803 := 0, AIADDR ($C00A) := 0
030b-0311   X:$1E40, X:$1E07, X:$1E08 and X:$180A written (zeros and one $FFFF)
0312-0317   X:$1800 := 0, X:$1801 := 0, Y:$2841 := $10, Y:$289E := $10
0318-031b   two more stores, at $05AB and $0020
031c-031d   ldc 0x5256,le / ldc 0x016d,ls        a hardware-loop hook (see below)
031e-0322   MODE & $1000 ? (recording)           then LE $3FE5 / LS $334 / LC $64 instead
0323-0324   jzc 0x3f84 / ldc 0x1880,i6           into the session routine with a fresh stack
```

The VSDSP4 core has one set of hardware loop registers: LS (loop start), LE (loop end) and LC (count). When the core
executes the instruction at address LE and LC is not zero, it decrements LC and continues at LS. VLSI uses this as a
hook: LE pointing into ROM and LS into IRAM gives a ROM routine a detour through RAM without any ROM being changed.
Their decoder-mode hook at $5256 fixes something in the hidden ROM; the IRAM code at $16D re-arms LC and jumps back.
The hooks fire deep inside decoding and keep firing, so the ROM must preserve LS/LE/LC across everything it does
between $3F84 and there.

Two consequences:

1. On the K2 bench (2026-09-07 12:0x) the patches took a chip from the synthesizer (started by the start plugin,
   AUDATA $AC45) to the decoder (AUDATA $1F40), and an MP3 played afterwards - "route A". That happened only because
   the K2's pins read GPIO & 3 = 0 at $3FB3. On a strapped board the same restart runs the check again and lands back
   in the synthesizer. Route A is not a fix.
2. The hook mechanism is exactly what a fix needs: restart the session the proven way, and detour around $3FB8-$3FD4.

## 5. The switcher, stage by stage

`mkswitcher.py` builds it; the 80 words are in `vs.asm` as the `Switch` table and on the disk as
`SYS/VSPLUGINS/switcher.plg`. Code at IRAM $50-$73:

```
0050-006b   VLSI's restart prologue, verbatim ($300-$31B above)
006c  ldc 0x3fb7,le        hook: after the ROM executes $3FB7 ...
006d  ldc 0x0071,ls        ... continue at the stub
006e  ldc 0x0001,lc
006f  j 0x3f84             restart the session
0070  ldc 0x1880,i6        (delay slot) fresh stack, as VLSI does
0071  ldc 0x0001,lc        the stub: re-arm for the next session
0072  j 0x3fd5             continue where an unstrapped chip continues
0073  nop
```

What happens, in order:

1. **Loading.** A plug-in is a list of records `[SCI register] [count, or count | $8000 for a repeated value]
   [value(s)]`. The switcher's records: WRAMADDR (register 7) := $8050, then 72 values to WRAM (register 6) - the 36
   instruction words, high half first, landing at I:$0050-$0073 - then AIADDR (register $A) := $0050. `vs` writes them
   with ordinary SCI commands through the bridge (`LoadTable` for the embedded copy, `LoadFile` for a file). The chip's
   SCI answers in both modes, and nothing is reset.
2. **The chip picks it up.** AIADDR is the firmware's application hook: at its next service pass the firmware calls the
   address written there. The K2 bench proved this works while the synthesizer is running: the patches loaded into a
   running synth restarted it.
3. **Prologue.** The chip clears the decoder's session variables the way VLSI's restart does: STATUS bit 15 off, AIADDR
   back to 0 so the plug-in is not called again, the X and Y locations listed above. The meaning is known for STATUS,
   AIADDR and X:$1E49 (the start plugin clears it too); the rest is copied unchanged from VLSI's code because that
   combination is proven.
4. **Hook and restart.** LE := $3FB7, LS := $71, LC := 1, and the core jumps to $3F84 with the stack pointer at $1880.
   From here the ROM runs its normal session start: registers saved, the init subroutines, AUDATA := $1F40.
5. **The detour.** At $3FB3 the ROM reads the pins - on a strapped board still GPIO & 3 = 2 - and computes the compare
   in $3FB4-$3FB6. After $3FB7 executes, the loop hardware finds LC = 1: LC := 0 and PC := $71. The stub re-arms
   LC := 1 and jumps to $3FD5, the address the ROM's own `jzc` at $3FB8 uses for an unstrapped chip. $3FBA-$3FD4 (the
   EarSpeaker fold, Y:$1B19 := 8 and `call $2135`) never run.
6. **Decoder session.** `call $27E1` at $3FD5 and the loop at $3FD7 service the SDI stream as on any decoder: file data
   in over SDI, HDAT0/HDAT1 show the format, DECODE_TIME counts decoded seconds, SM_CANCEL works. AUDATA reads $1F40
   until a file sets its rate ($AC45 for 44.1 kHz stereo - the same value the synthesizer uses, which is why AUDATA is
   a verdict only right after a switch).
7. **Later sessions.** When the stream ends, the session routine returns to the hidden main loop, which calls $3F84
   again. LS and LE are still set (VLSI's own hooks depend on the ROM preserving them) and the stub re-armed LC, so
   $3FB7 detours again: the chip stays a decoder until the next reset.
8. **After a reset**, hard or soft, the registers and IRAM are gone and the chip boots as the strap says. `vs` therefore
   runs `AutoSwitch` after every reset it performs (section 7).

The mode flag X:$C04C is not touched by the switcher. The K2 bench shows a restarted session comes up as the decoder
even when the flag had been set by the start plugin, and with $3FD3 skipped nothing sets it again.

## 6. The plug-in files (`SYS/VSPLUGINS`)

All four are raw big-endian 16-bit words in VLSI's record format; `vs -l <file>` streams any of them over SCI with no
reset before or after. Sources: `wildbits-buildkit\media\vsplugins\` (what the disks carry, overlaid onto the tree by
the build) and the text copies `wildbits-buildkit\vs1053\*.plg.txt`.

| file | words | what it does |
|---|---|---|
| `rtmidistart.plg` | 28 | VLSI's real-time MIDI start plugin (`rtmidistart.pdf`). Ten instructions at I:$50: writes X:$C01C, X:$1E49, AIADDR (0) and X:$C012 (1), then `call $2135` (X:$C04C := 1). The firmware starts the synthesizer: AUDATA $AC45, SDI bytes are MIDI events, General MIDI voices. `vs -n` sends the same words from its own copy (the `Plugin` table, step K of the test chain). |
| `rtmidistop.plg` | 28 | The start plugin with `call $213D` instead (X:$C04C := 0). An experiment, unproven: whether the synthesizer's loop notices a cleared flag lives in the hidden ROM. Not a cure for strapped boards either way, since the next session re-reads the pins. |
| `switcher.plg` | 80 | Section 5. `vs -o` sends the same words from the `Switch` table; `AutoSwitch` sends them after a reset when GPIO & 3 = 2. |
| `vs1053b_patches.plg` | 4667 | VLSI's patches package (`vs1053b-patches.pdf`): bug fixes hooked into the ROM, ending with the restart of section 4. Do not load it on a strapped board after the switcher: it takes over the single set of loop registers (the detour is gone) and its restart runs the strap check again, so the chip goes back to the synthesizer. Patches first and the switcher second is the order if both are wanted; the patches' $5256 hook is then inactive. |

## 7. What `vs` edition 10 does

- **AutoSwitch** runs after every reset `vs` performs: the hardware reset at the start of every run (all modes except
  `-i`, `-l`, `-u`, `-n`, `-o` and `-?`), and after each software reset (steps D and M of the test chain, and the
  "SM_CANCEL never cleared" fallback of `vs -s`). It reads GPIO_IDATA (WRAM $C018); when GPIO & 3 = 2 it sends the
  switcher, waits 6 ticks, reads AUDATA and prints
  `GPIO1 strap: switcher loaded, AUDATA $1F40  = stream decoder`.
  Any other AUDATA prints `vs: the switcher failed - the chip is still a MIDI synth` on stderr and exits with error 203
  (E$BMode). Under `vs -s` without `-d` the success line is silent like everything else; the error always shows.
- **`vs -n`** sends the start plugin, waits 3 ticks and prints `MIDI synth on: AUDATA $AC45  = real-time MIDI synth`.
- **`vs -o`** sends the switcher, waits 6 ticks and prints `MIDI synth off: AUDATA $1F40  = stream decoder`.
- **`vs -i`** (no reset) shows the pins and a verdict line: `GPIO0 = 1: SPI-boot strap, decoder (RT-MIDI cancelled)`,
  `GPIO1 = 1: RT-MIDI strap (synth) - vs -o or any reset switches it`, or `GPIO1 = 0: normal boot (stream decoder)`.
- **`vs -l <file>`** and **`vs -u aaaa nnnn <file>`** are the raw tools: any plug-in file in, any instruction range out.
- A step that never completes prints `VS1053: no response at step X` with the bridge registers; the new letters are W
  (AutoSwitch), Y (`-n`), Z (`-o`). Error 246 = the chip stopped answering, 203 = the switch failed.
- Run the `vs` that carries all this. When the machine boots from the SD card and the new disk is served over DriveWire,
  the shell's execution directory still points at the SD card's older `vs`, which ignores unknown switches and runs the
  full test chain instead: `chx /x0/cmds` first (`vs -?` must list `-n` and `-o`).

## 8. What is proven and what is not

Proven on the bench:

- The ROM facts of sections 3-5 (K2 dump, 2026-09-07).
- A plug-in sent over SCI restarts the firmware from inside a running synthesizer session (patches on the K2:
  AUDATA $AC45 to $1F40, then an MP3 played).
- The strap cannot be defeated from inside the chip and every reset re-samples it (Jr2, 2026-09-06).
- The pin 33-34 bridge (Jr2, 2026-09-06 22:1x): GPIO IN $0A03, decoder, files play.
- The switcher's restart and detour (K2, 2026-09-07 13:4x, the l2win 13:17 disk): `vs -n` turned the synthesizer on
  and `vs -o` brought the decoder back, both with the expected AUDATA verdicts. The first try ran the SD card's older
  `vs` and produced the full test chain instead - hence the `chx /x0/cmds` note in section 7.

Not yet proven:

- The detour's purpose - skipping $3FBA-$3FD4 - only matters when GPIO & 3 = 2, and no board here produces that now:
  the K2 reads 0, the bridged Jr2 reads 3. An unbridged bad-run Jr2 is the only real test. On such a board: `vs -i`
  (expect $0A02 and the GPIO1 verdict line), then `vs -r` (the hardware reset; AutoSwitch prints the switcher line),
  then `vs -s /dd/SOUNDS/mobygo.mp3`.
- That the ROM preserves LS/LE/LC from $3F84 to $3FB7 in decoder mode. VLSI's recording-mode hook (LE $3FE5) survives
  the same path and their decoder-mode hook survives far beyond it, so the assumption is sound, but it stays an
  assumption until the bench says otherwise. If "the switcher failed" appears, the fallback experiment is
  `vs -l /dd/SYS/VSPLUGINS/rtmidistop.plg`.
